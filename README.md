# LoL Lore Video Pipeline

**Self-hosted:** след сценария от Claude всичко (глас, картини, видео) се изпълнява локално на вашия Mac. Без API ключове, без абонаменти, без изпращане на данни навън.

От един `script.json` до готово ~10-минутно YouTube видео (16:9) с **истинско движение** (всяка сцена е 2–3 анимирани кадъра с cut-ове, като във филм, 30 fps; едни и същи герои във всички сцени и епизоди), 5–6 вертикални Shorts (9:16), субтитри, YouTube глави с реални таймкодове, 3 thumbnail варианта, фонова музика и метаданни за качване.

```
Claude (ръчно) ─► script.json ─► глас (Kokoro) ─► времева линия + аудио микс ─► картини (FLUX.2-klein + герои) ─► видео shots (LTX-2.5)
                                                                                                 │         или Ken Burns
                                          metadata / thumbnail / SRT ◄── Shorts 9:16 ◄── Master 16:9
```

## 1. Изисквания

- Mac с Apple Silicon (M1 или по-нов). Тествано на M5 Pro, 48 GB.
- Памет: 32 GB+ за истинско видео (видео моделът стига ~22 GB); с 16–24 GB ползвайте `LTX_LOW_RAM=1` или `--motion kenburns`.
- Диск: ~75 GB свободни (модели ~61 GB, Python среди ~3 GB, всеки епизод ~2–3 GB).
- Зарядно и отворен капак при рендер: епизод с истинско видео е няколко часа непрекъсната работа.
- Интернет само при първото пускане (теглене на моделите).
- [Homebrew](https://brew.sh).

## 2. Инсталация

**1) Системни пакети.** Трябва `ffmpeg-full`, не обикновеният `ffmpeg`: обикновената Homebrew версия вече е без libass и субтитрите тихо не се изпичат във видеото.

```bash
brew install ffmpeg-full python@3.12 espeak-ng git
brew uninstall ffmpeg 2>/dev/null; brew link --force ffmpeg-full    # ffmpeg-full става системният ffmpeg
ffmpeg -hide_banner -filters | grep -E " (subtitles|loudnorm) "      # трябва да покаже и двата реда
```

`espeak-ng` се ползва от Kokoro за думи, които не са в речника му.

**2) Кодът.**

```bash
git clone https://github.com/ikonomovdaniel2-cpu/VideoProducing.git LoL_Video_Pipeline
cd LoL_Video_Pipeline
```

(Репото е private: трябва достъп до него и вход в GitHub, например с `brew install gh && gh auth login`.)

**3) Python среда.**

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements-local.txt
cp .env.example .env        # настройките по подразбиране са self-hosted, нищо не е задължително
```

**4) Модели (еднократно, автоматично).** При първото пускане се теглят от Hugging Face в `~/.cache/huggingface`:

| Какво | Размер | Нужен ли е вход |
|---|---|---|
| Kokoro-82M (глас) | ~330 MB | не |
| spaCy `en_core_web_sm` (ползва се от Kokoro, инсталира се сам във `.venv`) | ~13 MB | не |
| FLUX.2-klein-4B (картини, по подразбиране) | ~16 GB | не |
| LTX-2.5 distilled, int8 (видео, виж стъпка 5) | ~45 GB | да (лиценз) |

При 3–4 MB/s връзка картините и гласът са около 1.5 часа, видео моделът още ~2–4 часа. След това всичко работи и без интернет (`export HF_HUB_OFFLINE=1`, ако искате да го гарантирате).

**5) Истинско видео: LTX-2.5 (отделна среда).** Видео моделът има свои зависимости, затова живее в отделна среда `.venv-ltx`; пайплайнът я вика сам.

```bash
python3.12 -m venv .venv-ltx
.venv-ltx/bin/pip install --upgrade pip
.venv-ltx/bin/pip install -r requirements-ltx.txt
```

Моделът (`dgrauet/ltx-2.5-mlx-q8`) е gated – приема се лицензът на Lightricks (безплатен за създатели под $10M годишни приходи):

1. Безплатен акаунт на https://huggingface.co/join и Read token от https://huggingface.co/settings/tokens.
2. На https://huggingface.co/dgrauet/ltx-2.5-mlx-q8 натиснете **Agree and access repository** (одобрява се веднага).
3. `hf auth login` (в активираната `.venv`), поставете токена.

При първия рън с истинско видео се теглят ~45 GB (само нужните части от пакета, без dev модела). Може и предварително:

```bash
hf download dgrauet/ltx-2.5-mlx-q8 --exclude "transformer-dev.safetensors" --exclude "*distilled-lora*"
```

Без тази стъпка пайплайнът работи с `--motion kenburns` (картина + zoom/pan).

**По желание: FLUX.1-schnell.** Вече е gated модел в Hugging Face. Ако искате да го ползвате:

1. Безплатен акаунт на https://huggingface.co/join.
2. На https://huggingface.co/black-forest-labs/FLUX.1-schnell натиснете **Agree and access repository** (одобрява се веднага).
3. Read token от https://huggingface.co/settings/tokens, после в терминала:


## 4. Първи тест

```bash
python run_pipeline.py --input script.example.json --dry-run
```

Използва placeholder картини и вградения macOS глас (`say`), без да зарежда модели. Отнема под минута и проверява, че FFmpeg и целият път до готовите видеа работят. После с истинските модели (първия път тегли теглата, виж т.2):

```bash
python run_pipeline.py --input script.example.json
```

Резултатът е в `output/darius_lore_ep1/`.

## 5. Реален епизод

1. Отворете `claude_prompt.md`, заменете темата и езика, поставете в Claude.
2. Запишете отговора в `script.json` (може с ```json оградите – скриптът ги чисти). В репото има готов пример: пълен епизод за Darius. Всяка сцена има `shots`: 2–3 кадъра от един и същ момент (напр. wide → medium → close-up), всеки с `image_prompt` (картината) и `video_prompt` (какво се движи и едно движение на камерата). По-стари сценарии само с `image_prompt`/`video_prompt` на сцена също работят: shots се правят автоматично.
3. Проверка без разходи (валидация + оценка на дължината):
   ```bash
   python run_pipeline.py --input script.json --check
   ```
4. Пълен рън:
   ```bash
   python run_pipeline.py --input script.json
   ```

Резултат:

```
output/<project_name>/
├── Master.mp4        # 1920x1080 @30fps, H.264 + AAC, -14 LUFS, изпечени субтитри, фонова музика
├── Master.srt        # качете го в YouTube Studio като субтитри (по-добро от авто-генерираните)
├── Short_01..06.mp4  # 1080x1920, заглавие отгоре, TikTok-стил субтитри с подсветка на думата
├── thumbnail.jpg     # 1280x720 (+ thumbnail_2.jpg, thumbnail_3.jpg за A/B теста)
├── metadata.txt      # заглавия (+ варианти за A/B), описание с глави и кредити за музиката, тагове – за copy-paste
├── metadata.json     # същото, машинно-четимо
├── render_report.md  # отчет от ръна: настройки, време по етапи, LTX статистика, заспивания на Mac-а, проверка
└── _work/            # кеш (глас, картини, клипове)
```

**Къде се вижда прогресът:**
- в терминала: лог за всяка стъпка (`[2/6] Изображения`, `Сцена 14: изображение готово` …); при видеото всеки готов кадър (shot) показва времето си и колко остава (`🎥 Сцена 9 (2): 156s … остават ~6:40:00`); `-v` за подробности;
- във Finder: `output/<project_name>/_work/images/raw/` се пълни с картини, а `_work/motion/raw/` с видео клипове, един по един;
- Activity Monitor → процесът `python`; Window → GPU History показва натоварването при картините.

**Защита от заспиване:** пайплайнът сам пуска `caffeinate` за времето на ръна (спира заедно с него), така че Mac-ът не заспива от неактивност. Затворен капак на батерия обаче пак приспива Mac-а и спира рендера (продължава при събуждане, нищо не се губи), затова при видео рендер на батерия пайплайнът предупреждава: включете зарядното и дръжте капака отворен. Ако Mac-ът все пак е заспал, `render_report.md` показва кога, колко дълго и защо (напр. `Clamshell Sleep`, `Thermal Emergency Sleep`).

**Автоматична проверка:** в края на всеки рън файловете се проверяват (формат, синхрон, -14 LUFS, Shorts, субтитри, глави, thumbnail) и резултатът е в лога и в `render_report.md`. Ръчно: `python tools/verify_output.py output/<project_name>`.

`output/` не се качва в git (видеата са над лимита на GitHub).

## 6. Кеширане и редакции

Всеки глас, картина и клип се кешира по хеш на съдържанието си. Ако промените текста на сцена 14, при следващото пускане се генерира наново **само** гласът на сцена 14 (и картината ѝ, ако сте сменили промпта), а всичко останало се взима от кеша. Тест на 66-сценов епизод: редакция на една сцена = ~3 мин вместо ~57 мин. Прекъснат рън (Ctrl+C, мрежова грешка, заспал Mac) просто се пуска отново. `--force` игнорира кеша; `--clean` трие `_work/` след успех.

Удобен цикъл: генерирайте, прегледайте картините в `_work/images/raw/`, изтрийте файловете, които не ви харесват (или сменете `image_prompt`), пуснете отново.

## 7. CLI флагове

| Флаг | Действие |
|---|---|
| `--input`, `-i` | път до сценария (по подразбиране `script.json`) |
| `--dry-run` | placeholder картини + `say` глас, без зареждане на модели |
| `--check` | само валидация и оценка |
| `--preview "текст"` | озвучава само този текст (проба на глас и произношение) |
| `--tts kokoro\|say\|silent\|elevenlabs` | избор на глас |
| `--images mflux\|comfyui\|placeholder\|fal\|replicate` | избор на генератор |
| `--motion ltx\|kenburns` | истинско видео (LTX-2.5) или картина + zoom/pan |
| `--res 1080\|4k` | резолюция на мастъра |
| `--layout zoom\|blur\|crop` | оформление на Shorts |
| `--music path` | фонова музика (файл или папка) с автоматично заглушаване под гласа |
| `--encoder libx264` | софтуерен енкодер вместо хардуерния |
| `--no-subs`, `--no-shorts` | изключва съответната част |
| `--force`, `--clean`, `-v` | регенерация / почистване / подробен лог |

Всяка настройка от `.env` може да се смени и само за един рън, например:

```bash
MFLUX_MODEL=schnell KOKORO_VOICE=bm_george KOKORO_LANG=b python run_pipeline.py -i script.json
```

## 9. Локални модели

### Глас: Kokoro
82M-параметров невронен TTS с лиценз Apache 2.0. 66 сцени се озвучават за ~1.5 мин и Kokoro връща тайминг на всяка дума, така че субтитрите съвпадат точно. Опитайте няколко гласа с `--preview` и изберете (`KOKORO_VOICE`). Kokoro поддържа английски и няколко други езика, но не и български.

### Картини: mflux
Flux модели, пренаписани за Apple MLX, работят директно на GPU-то на Mac-а, без отделен сървър. Моделът се зарежда веднъж и генерира всички сцени една след друга.

| `MFLUX_MODEL` | Лиценз | Вход в HF | Бележки |
|---|---|---|---|
| `flux2-klein-4b` **(по подразбиране)** | Apache 2.0 | не | 4 стъпки, ~48 s/картина на M5 Pro. Чете дълги промптове, затова описанията на героите се спазват най-добре. |
| `schnell` | Apache 2.0 | **да** (виж т.2) | 4 стъпки, ~56 s/картина, по-кинематографичен вид, но текстовият му енкодер чете само ~256 токена и губи детайли от описанията (в теста Darius получи брада, която я няма в описанието). |
| `dev` | **некомерсиален** (Black Forest Labs) | да | 25 стъпки, по-бавен. Прочетете лиценза, преди да го ползвате за монетизиран канал. |

### Видео: LTX-2.5 (истинско движение)
22B видео модел на Lightricks (август 2026), в distilled режим за скорост, през MLX порта [ltx-2-mlx](https://github.com/dgrauet/ltx-2-mlx) (MIT). Всяка сцена се монтира като във филм:

- сцената се дели на 2–3 **shots** по ~4 s (wide → medium → close-up на един и същ момент), с твърди cut-ове между тях;
- всеки shot тръгва от **собствена** картина (с героите от библиотеката, т.10) и се анимира по своя `video_prompt` в нативни 30 fps. Няма верижно продължение от последния кадър, затова героите не се променят от shot на shot и камерата не „диша“ (zoom навътре и после навън – проблемът на първата версия);
- едно бавно движение на камерата на shot (push-in, truck, arc, handheld, tilt), никога едно и също два пъти подред; силни движения (crane, dolly, zoom) моделът преиграва и `--check` предупреждава за тях;
- негативен промпт (`LTX_NEGATIVE`, през NAG) пази от „дишащ“ zoom, бърза камера, морфинг на лица и подписи;
- **автоматична проверка:** мащабът на всеки нов shot се мери кадър по кадър; при zoom навътре-навън, рязък скок или над 30% zoom shot-ът се генерира наново с друг seed (`SHOT_RETRIES`), а `render_report.md` казва колко са били;
- генерира се в 1024x576 (два етапа: половин резолюция + 2x upscale и доизчистване), после се мащабира до 1920x1080 с леко филмово зърно (`FILM_GRAIN`); всеки shot се реже до точния брой кадри от времевата линия, така че гласът и субтитрите остават в синхрон;
- моделът работи в отделен процес (`tools/ltx_worker.py` в `.venv-ltx`), зарежда се веднъж за всички сцени и се освобождава в края;
- всеки shot се кешира: прекъснат рън продължава от мястото, където е спрял.

Най-добре се получават бавни, ясни движения (вятър, огън, дим, дъжд, маршируващи редици, бавни движения на камерата); бързи битки и сложни движения на ръцете стават по-лошо. Лицензът е LTX-2 Community License – безплатен под $10M годишни приходи.

`--motion kenburns` връща старото поведение (картина + плавен zoom/pan, минути вместо часове).

### Картини: ComfyUI (за повече контрол)
Ползвайте го, ако искате SDXL, LoRA за конкретен стил, upscaler или собствен workflow.
1. Инсталирайте ComfyUI Desktop (comfy.org) и сложете модела в `ComfyUI/models/checkpoints/`.
2. Направете работещ workflow (1920x1088 за Flux, 1344x768 за SDXL).

## 10. Консистентни герои и произношение

### Герои
Flux не познава героите на League, а всеки кадър се генерира отделно. Без помощ Darius ще изглежда различно във всяка сцена. Затова сценарият има секция `characters`:

```json
"characters": {
  "darius": "a towering broad-shouldered warrior in his forties, short-cropped black hair with grey streaks, scarred stern face, heavy black and crimson plate armor ...",
  "darius_young": "a gaunt dark-haired boy of about ten ..."
}
```

В `image_prompt` героят се споменава като `{darius}`, а пайплайнът вмъква точно същото описание във всяка сцена. Различни възрасти или форми са отделни ключове. `--check` хваща недефинирани `{ключ}`, имена, написани без скоби (тогава описанието не се вмъква), неизползвани герои и твърде дълги промптове (важно за schnell, който чете ~256 токена).

**Библиотека с герои (FLUX.2-klein, `CHARACTER_REFS=1`):** за всеки герой пайплайнът прави веднъж референтен портрет (цяла фигура, неутрален фон) в `characters/<ключ>_<хеш>.png`. Всяка картина с `{darius}` се генерира **от този портрет** (FLUX.2-klein приема референтни картини), не само от текста. Така лицето, косата и костюмът са едни и същи в wide, medium и close-up, във всички сцени и във всички епизоди, които ползват същото описание.

- Портретът зависи от описанието: промените ли го, се прави нов (старият остава за старите епизоди). Не ви харесва портретът? Променете леко описанието или изтрийте файла и сменете дума.
- В една картина може да има до 3 героя с портрет.
- `characters/` не се качва в git; при нужда портретите се генерират наново.

### Произношение
Речникът променя текста **само за гласа**. Субтитрите остават с правилното изписване, защото таймингите се връщат към оригиналните думи.

- `pronunciations.json`: глобален речник за всички епизоди (има стартов списък с имена като Kha'Zix, Rek'Sai, LeBlanc, Freljord...).
- `"pronunciations"` в `script.json`: за конкретния епизод, с предимство пред глобалния. Claude ги генерира по промпта.
- Стойност: фонетичен правопис с тирета (`"Kah-Zix"`) или IPA в наклонени черти (`"/kəzˈɪks/"`, само за Kokoro).
- Работи и за притежателни форми (`Kha'Zix's`) и имена от няколко думи.

Проба без да пускате целия пайплайн (пуска и звука):
```bash
python run_pipeline.py --preview "Kha'Zix hunts in the Void beneath Shurima."
python run_pipeline.py -i script.json --preview "..."   # + речника от сценария
```

`--check` показва кои записи от речника се ползват и предупреждава за имена с апостроф (тип `Xin'Zhao`), които липсват. Промяна в речника регенерира гласа само на засегнатите сцени.

## 14. Какво е поправено/подобрено

Спрямо оригиналната спецификация:

- **moviepy е премахнат.** `moviepy.editor` не съществува в moviepy 2.x, а и рендерирането през Python кадър по кадър е многократно по-бавно. Всичко минава през FFmpeg.
- **Кадрово точен синхрон.** Всяка сцена е цяло число кадри, аудиото ѝ е допълнено до точно `кадри × 1600` семпъла (48 kHz / 30 fps). Гласът и картината не се разминават дори след 75 сцени. Целият разказ е един непрекъснат WAV, така че няма щракания между сцените.
- **Ken Burns без трептене.** Наивният `zoompan` „трепери“, защото закръгля координатите до цели пиксели; тук картината се супер-семплира до ~8K преди движението. Движенията се редуват (zoom in/out, pan) вместо само zoom-in.
- **Shorts не се режат от мастъра.** Shorts се сглобяват от чистите клипове на сцените, с отделни вертикални субтитри и заглавие.
- **Истински субтитри** по реалния тайминг на всяка дума (Kokoro, ElevenLabs); при `say`/`silent` се изчисляват пропорционално.
- **YouTube глави с реални таймкодове.** Claude пише `{{CHAPTERS}}`, а пайплайнът го попълва след генерирането на гласа и спазва правилата на YouTube (първа глава 0:00, всяка ≥10 s).
- **Звук по стандарт:** -14 LUFS (нивото на YouTube) и по желание фонова музика с автоматично заглушаване под гласа (sidechain).
- **Валидация преди разходи**, **retry с backoff**, **консистентни герои** и **речник за произношение**.
- **Self-hosted по подразбиране:** Kokoro за глас и Flux през MLX (или ComfyUI) за картини. Облачните услуги са само опция.

При инсталацията (октомври 2026, подробности в `DEPLOYMENT_REPORT.md`):

- **Pillow<13**: Pillow 13 чупи mflux на Python 3.12.
- **mflux 0.23**: поддръжка на новото API (иначе моделът се презарежда за всяка сцена).
- **Силата на звука** вече реално е -14 LUFS (еднопасовият loudnorm оставаше на ~-15.5).
- **Ясна грешка при gated модели** + нова опция `MFLUX_MODEL=flux2-klein-4b`, която стана основният модел.
- **ffmpeg-full** вместо slim `ffmpeg` (заради субтитрите).

- **Истинско видео вместо слайдшоу** (октомври 2026): всяка сцена се анимира локално от LTX-2.5 в 30 fps, с кадрово точен синхрон с гласа (т.9).
- **Монтаж като във филм вместо едно дълго продължение** (октомври 2026): първата версия правеше всяка сцена като 11-секунден клип от 3 части, всяка продължаваща от последния кадър на предишната. Анализът на целия епизод показа два проблема: в 36 сцени zoom-ът се връщаше навътре-навън (до ±100%), а героите се променяха от част на част. Сега: 2–3 shots с cut-ове, всеки от собствена картина с героите от библиотеката, едно бавно движение на камерата, негативен промпт и автоматична проверка с нов опит. В теста zoom-ът падна от ±40–100% на 0–16% в една посока, а лицата и костюмите останаха същите във всички кадри.
- **Шевове между shots:** shot-ът се генерира с 1–7 кадъра повече (LTX иска 8k+1 кадъра), а следващият продължава от последния му кадър. Първата версия режеше излишъка от всеки shot и на шева се прескачаха до 7 кадъра (видимо подскачане). Сега shot-овете се ползват цели и се реже само краят на последния; движението на шева е ~1.1× нормалното (беше ~3.2×). Поправката не изисква нов рендер: суровите shots са в кеша.

## 15. Растеж в YouTube и TikTok

Алгоритмите и на двете платформи показват видеото на повече хора, ако го **кликат** (thumbnail + заглавие) и **гледат докрай** (особено първите 30 s; при Shorts/TikTok – първата 1 s, гледане докрай, повторно гледане, споделяния). Какво е вградено в пайплайна за това:

| Сигнал | Какво прави пайплайнът |
|---|---|
| Клик (CTR) | 3 варианта на thumbnail със собствена картина (лице отблизо, силна емоция, текст до 4 думи) + 2 алтернативни заглавия → качете ги в YouTube Studio → **Test & Compare** |
| Задържане в началото | `claude_prompt.md` изисква cold open (най-драматичният момент първо), обещание до 30-ата секунда и „отворени въпроси“ на ~60 s |
| Задържане по-нататък | истинско видео с движение, фонова музика със заглушаване под гласа, глави, ескалация по глави |
| Shorts / TikTok | 5–6 Shorts на епизод (25–45 s), кука в първото изречение, край, който се връзва с началото (повторно гледане), `zoom` оформление, субтитри с подсветка |
| Оригиналност | промптът иска собствен ъгъл и различна структура за всеки епизод – YouTube демонетизира канали с „шаблонно“ съдържание |

Качване: YouTube приема качването ръчно или през официалния API (планирано). TikTok позволява автоматично публикуване само на одобрени приложения, затова Shorts се качват ръчно (заглавие и описание са в `metadata.txt`). AI етикет: YouTube и TikTok изискват етикет за реалистично AI съдържание; при съмнение го включете – не намалява показванията.
